1. PROJECT OVERVIEW & PROBLEM STATEMENT
================================================================================

HealthDekho is a full-stack, customer-facing Insurance Management System built to
replace manual insurance discovery, advisory, and policy onboarding workflows
with a secure, deterministic, and auditable web application.

Core Capabilities Implemented:
- FR-1: Customer Authentication, Customer Dashboard, and Product Catalog Discovery
  * Customers can sign up, sign in with JWT bearer authentication, view their
    personal profile, inspect their registered policies, and browse active
    insurance products they have not yet registered.
- FR-2: AI-Powered Insurance Recommendations & Audit History
  * Customers enter insurance goals, date of birth, preferred policy term, and
    preferred insurance type. The backend filters eligible products first, sends
    only valid candidates to Amazon Bedrock (Claude Haiku 4.5) via Spring AI
    ChatClient, validates the AI JSON strictly against the database snapshot,
    persists every request/outcome, and displays explainable recommendations
    plus full recommendation history.
- FR-3: Atomic Policy Registration, Installment Schedule & Policy Details
  * Customers review applicant & product details and register a policy using an
    idempotency key. The backend atomically creates the policy, generates a
    concurrency-safe sequential policy number (HD-YYYY-000001), and generates
    the complete premium installment schedule inside one database transaction.

Important Domain Boundary:
- AI is strictly ADVISORY only. AI never computes age, eligibility, premiums,
  or sum insured, and never approves policy registration.
- Claims and payment gateway transfers are intentionally out of scope (though
  the `premium_payment` table/entity is modeled in the schema foundation).

3. HOW THE PROJECT IS BUILT (ARCHITECTURE & PROJECT STRUCTURE)
================================================================================

HealthDekho follows a **Modular Monolith with Layered Architecture** on the
backend and a **Decoupled Single-Page Application (SPA)** on the frontend.

A. Backend Architecture (Layered Flow)
--------------------------------------
Request Flow:
  HTTP Request
    -> SecurityFilterChain + JwtAuthenticationFilter (verifies JWT, sets Principal)
    -> @RestController (accepts/returns DTOs, validates input with @Valid)
    -> @Service / ServiceImpl (business rules, eligibility, transactions)
    -> JpaRepository (PostgreSQL persistence) / ChatClient (Bedrock AI)
    -> @RestControllerAdvice (GlobalExceptionHandler -> application/problem+json)

Key Architectural Rule:
- JPA `@Entity` objects NEVER leave the service/repository layer directly as API
  payloads. Controllers only accept and return Java `record` DTOs.
- Customer identity (`customerId`) is ALWAYS extracted from the verified JWT's
  `sub` claim via `@AuthenticationPrincipal CustomerPrincipal`, never trusted
  from request payloads or query parameters.

Backend Package Structure (`backend/src/main/java/com/healthdekho/`):
- `HealthdekhoApplication.java`    : Spring Boot entry point
- `config/`
  * `SecurityConfig.java`          : Stateless security rules, BCrypt, JWT filter
  * `BedrockAiConfig.java`         : Exposes Spring AI `ChatClient` bean
- `constants/`
  * `ApiErrorCodes.java`           : Stable machine-readable API error codes
- `controller/`
  * `AuthController.java`          : `/api/v1/auth/login`, `/api/v1/auth/register`
  * `CustomerController.java`      : `/api/v1/customers/me`, `/me/policies`
  * `DashboardController.java`     : `/api/v1/dashboard`
  * `ProductController.java`       : `/api/v1/products/available`, `/{productCode}`
  * `PolicyController.java`        : `/api/v1/policies`, `/{policyNumber}`
  * `RecommendationController.java`: `/api/v1/recommendations`, `/history`
- `dto/`                           : 18 immutable Java `record` Request/Response DTOs
- `entity/`                        : 7 JPA `@Entity` domain classes
- `exception/`                     : Custom domain exceptions + `GlobalExceptionHandler`
- `repository/`                    : 7 `JpaRepository` interfaces
- `security/`                      : `JwtService`, `JwtAuthenticationFilter`,
                                     `CustomerPrincipal`, `CustomUserDetailsService`
- `service/` & `service/impl/`     : Interfaces and implementations for Auth,

4. DATABASE SCHEMA & ALL 7 JPA ENTITIES (POSTGRESQL)
================================================================================

All 7 tables use `UUID` primary keys (`@GeneratedValue(strategy = GenerationType.UUID)`)
and `NUMERIC(19,2)` (`precision = 19, scale = 2`) for all monetary values.

1. `customer` (`Customer.java`)
   - Columns: `id` (PK, UUID), `first_name` (100), `last_name` (100),
     `email` (254), `normalized_email` (254, UNIQUE), `password_hash` (100),
     `date_of_birth` (LocalDate), `mobile_number` (30, UNIQUE), `active` (boolean,
     default true), `created_at` (`@CreationTimestamp`), `updated_at` (`@UpdateTimestamp`).
   - Purpose: Stores customer identity and BCrypt credentials. Email is
     normalized to trimmed lowercase so login/uniqueness is case-insensitive.

2. `insurance_product` (`InsuranceProduct.java`)
   - Columns: `id` (PK, UUID), `product_code` (50, UNIQUE), `name` (150),
     `product_type` (50 — e.g. HEALTH, LIFE, RETIREMENT, EDUCATION),
     `term_months` (Integer), `sum_insured` (NUMERIC 19,2),
     `premium_per_installment` (NUMERIC 19,2), `premium_frequency` (30 —
     MONTHLY, QUARTERLY, HALF_YEARLY, YEARLY), `min_age` (Integer),
     `max_age` (Integer), `active` (boolean, default true).
   - Purpose: Master insurance catalog.

3. `customer_policy` (`CustomerPolicy.java`)
   - Columns: `id` (PK, UUID), `customer_id` (FK -> `customer`, LAZY),
     `product_id` (FK -> `insurance_product`, LAZY), `policy_number` (64, UNIQUE),
     `registration_idempotency_key` (UUID), `start_date`, `maturity_date`,
     `product_name`, `product_type`, `term_months`, `premium_frequency`,
     `premium_per_installment` (19,2), `sum_insured` (19,2),
     `total_premium` (19,2), `status` (30, e.g. `ACTIVE`), `registered_at`.
   - Unique Constraints:
     * `uq_customer_policy_product` on `(customer_id, product_id)` -> prevents
       registering the same product twice at DB level.
     * `uq_customer_policy_registration_idempotency` on
       `(customer_id, registration_idempotency_key)` -> guarantees idempotent retries.
   - Design Note: Snapshots product name, type, term, frequency, premium, and
     sum insured onto the policy row so future catalog edits never alter an
     already-issued policy contract!

4. `premium_installment` (`PremiumInstallment.java`)
   - Columns: `id` (PK, UUID), `policy_id` (FK -> `customer_policy`, LAZY),
     `installment_number` (Integer), `due_date`, `grace_date`,
     `scheduled_amount` (19,2), `paid_amount` (19,2), `status` (30, e.g. `PENDING`).
   - Unique Constraint: `uq_installment_policy_number` on `(policy_id, installment_number)`.
   - Purpose: Complete installment schedule generated atomically when a policy
     is registered.

5. `premium_payment` (`PremiumPayment.java`)
   - Columns: `id` (PK, UUID), `installment_id` (FK -> `premium_installment`, LAZY),
     `transaction_reference` (150, UNIQUE), `idempotency_key` (UUID, UNIQUE),
     `paid_at`, `amount` (19,2), `penalty_amount` (19,2), `payment_method` (50),
     `created_at`.
   - Purpose: Schema entity modeling payment records per installment.

6. `ai_recommendation_request` (`AIRecommendationRequest.java`)
   - Columns: `id` (PK, UUID), `customer_id` (FK -> `customer`, LAZY),
     `goals` (2000), `preferred_term_months` (Integer),
     `preferred_product_type` (50), `calculated_age` (Integer),
     `status` (30: `PENDING`, `NO_RESULTS`, `SUCCEEDED`, `FAILED`),
     `model_id` (200), `prompt_version` (100),
     `candidate_snapshot` (`@JdbcTypeCode(SqlTypes.JSON)` storing serialized
     candidate products sent to AI), `created_at`.
   - Purpose: Immutable audit trail of every AI recommendation invocation.

7. `ai_recommendation_item` (`AIRecommendationItem.java`)
   - Columns: `id` (PK, UUID), `request_id` (FK -> `ai_recommendation_request`, LAZY),
     `product_id` (FK -> `insurance_product`, LAZY), `reason` (2000),
     `suitability` (100), `rank` (Integer), `selected` (boolean).
   - Unique Constraint: `uq_recommendation_request_product` on `(request_id, product_id)`.
   - Purpose: Stores only validated recommendations linked to real DB products.

--------------------------------------------------------------------------------
5.1 Cross-Cutting Implementations
--------------------------------------------------------------------------------
1. Standardized Problem Details Errors (`application/problem+json`):
   - `GlobalExceptionHandler` (`@RestControllerAdvice`) and `ApiProblemWriter`
     (used inside Spring Security handlers where MVC advice doesn't run) return
     a consistent JSON shape:
       {
         "type": "about:blank",
         "title": "...",
         "status": 409,
         "detail": "...",
         "code": "DUPLICATE_POLICY",
         "traceId": "<random-uuid>"
       }
   - On validation failures (`MethodArgumentNotValidException`), a `fieldErrors`
     map (`fieldName -> errorMessage`) is also included with HTTP 400 and code
     `VALIDATION_FAILED`.
   - Defined error codes in `ApiErrorCodes.java`:
     * `VALIDATION_FAILED` (400)
     * `INVALID_PAGINATION` (400)
     * `AUTHENTICATION_FAILED` (401)
     * `UNAUTHENTICATED` (401)
     * `PRODUCT_NOT_FOUND` (404)
     * `POLICY_NOT_FOUND` (404)
     * `CUSTOMER_REGISTRATION_CONFLICT` (409)
     * `PRODUCT_UNAVAILABLE` (409)
     * `DUPLICATE_POLICY` (409)
     * `AGE_NOT_ELIGIBLE` (422)
     * `AI_RECOMMENDATION_UNAVAILABLE` (502)
     * `INTERNAL_ERROR` (500)

2. Monetary Precision:
   - Uses `java.math.BigDecimal` everywhere, never `double`/`float`.
   - `MoneyFormatter.format(BigDecimal)` formats monetary values with
     `setScale(2, RoundingMode.HALF_UP).toPlainString()`.

3. Hibernate / JPA Best Practice:
   - `spring.jpa.open-in-view=false` prevents accidental lazy-loading queries
     during JSON serialization in controllers and keeps database connections
     scoped cleanly to service transactions.

--------------------------------------------------------------------------------
5.2 Authentication & Security Implementation
--------------------------------------------------------------------------------
Endpoints:
- `POST /api/v1/auth/register` (Public)
- `POST /api/v1/auth/login`    (Public)
- All other endpoints require a valid `Authorization: Bearer <token>` header.

How `SecurityConfig.java` works:
- CSRF is disabled because the API is stateless and does not use cookie auth.
- `SessionCreationPolicy.STATELESS`: Spring Security never creates HTTP sessions.
- Permits `/api/v1/auth/login` and `/api/v1/auth/register`; all other requests
  require authentication.
- Registers `JwtAuthenticationFilter` before `UsernamePasswordAuthenticationFilter`
  and disables servlet auto-registration (`FilterRegistrationBean.setEnabled(false)`)
  so the filter runs exactly once inside Spring Security's filter chain.
- Uses `BCryptPasswordEncoder(12)` (cost factor 12).
- Custom `authenticationEntryPoint` (401 `UNAUTHENTICATED`) and
  `accessDeniedHandler` (403 `FORBIDDEN`) write `application/problem+json`.

How Registration (`AuthenticationServiceImpl.register`) works:
1. Validates `RegisterRequest`:
   - `firstName`, `lastName` (NotBlank, max 100)
   - `email` (NotBlank, `@Email`, max 254)
   - `mobileNumber` (`@Pattern("^[+]?[0-9][0-9\\s-]{6,29}$")`, length 7-30)
   - `dateOfBirth` (`@NotNull`, `@PastOrPresent`)
   - `password` and `confirmPassword` (8-72 chars)
   - `@AssertTrue isPasswordsMatching()`
   - `@AssertTrue isPasswordBcryptCompatible()` checks UTF-8 byte length <= 72
     (important because BCrypt silently truncates inputs beyond 72 bytes!).
2. Normalizes email (`trim().toLowerCase(Locale.ROOT)`) and mobile number
   (strips spaces and hyphens via `replaceAll("[\\s-]+", "")`).
3. Checks `existsByNormalizedEmail` and `existsByMobileNumber`; also catches
   `DataIntegrityViolationException` for race-condition safety -> throws
   `CustomerRegistrationConflictException` (409).
4. Hashes password with BCrypt, saves `Customer`, returns HTTP 201 with
   `RegisterResponse(customerId, "Customer registered successfully")`.

How Login (`AuthenticationServiceImpl.login`) & JWT (`JwtService`) work:
1. Normalizes email and delegates to `AuthenticationManager.authenticate(...)`,
   which uses `CustomUserDetailsService.loadUserByUsername(...)` and verifies
   BCrypt hash. Failures throw `AuthenticationFailedException` (401).
2. Verifies customer is still `active`.
3. `JwtService.issueAccessToken(customer)` builds an HS256 JWT containing:
   - `sub`: `customer.getId().toString()` (UUID)
   - `email`: normalized email
   - `role`: `"CUSTOMER"`
   - `iss`: configured `JWT_ISSUER`
   - `aud`: configured `JWT_AUDIENCE`
   - `iat`: current instant
   - `exp`: `iat + 10 minutes` (600 seconds)
4. Returns `LoginResponse(accessToken, "Bearer", 600)`.

How `JwtAuthenticationFilter` & `JwtService.validateAndLoadPrincipal` work:
- Reads `Authorization` header starting with `"Bearer "`.
- Parses and verifies signature with `signingKey` and `requireIssuer(issuer)`.
- Strictly verifies:
  * Algorithm is `HS256` (prevents `alg=none` or algorithm confusion attacks)
  * Expiration (`exp`) is present and valid
  * Audience (`aud`) contains configured `audience`
  * `role` claim equals `"CUSTOMER"`
  * `sub` is a valid UUID
  * Customer exists in DB, `isEnabled()` (`active == true`), and `email` claim
    still matches `principal.getUsername()`
- Sets `UsernamePasswordAuthenticationToken` into `SecurityContextHolder`; any
  exception clears the security context so Spring Security rejects with 401.

Frontend Auth Implementation (`session.js`, `AuthContext.jsx`, `client.js`):
- Stores `healthdekho.accessToken` and `healthdekho.customer` in
  `window.sessionStorage` (tab-local rather than `localStorage` to limit cross-tab
  exposure).
- Dispatches a custom window event `healthdekho:session-change` whenever session
  storage updates so React context stays synchronized.
- On app mount, if a token exists in `sessionStorage`, `AuthProvider` calls
  `GET /api/v1/customers/me` to validate it; if invalid/expired, clears session
  and sets status to `"anonymous"`.
- Axios request interceptor injects `Authorization: Bearer <token>`.
- Axios response interceptor automatically calls `clearSession()` on any HTTP
  `401` response if a token was present.
- `ProtectedRoute` renders a loading indicator while `status === "checking"`
  and redirects to `/login` if `status !== "authenticated"`.

5.3 Dashboard & Product Catalog Discovery (FR-1)
--------------------------------------------------------------------------------
Endpoints:
- `GET /api/v1/customers/me` -> `CustomerProfile` (id, firstName, lastName,
  email, mobileNumber, dateOfBirth)
- `GET /api/v1/customers/me/policies` -> `List<PolicySummaryResponse>` sorted
  by `startDate DESC, policyNumber ASC`
- `GET /api/v1/dashboard` -> `DashboardResponse` (customer summary, policyCount,
  and policies list)
- `GET /api/v1/products/available?page=0&size=20` -> `AvailableProductsResponse`
  (items, page, size, totalElements, totalPages)
- `GET /api/v1/products/{productCode}` -> `ProductDetailResponse`

Key Backend Logic:
- `InsuranceProductRepository.findAvailableForCustomer(customerId, pageable)`
  uses a JPQL `NOT EXISTS` subquery to return ONLY products where `active = true`
  AND the authenticated customer does not already have a `CustomerPolicy` for
  that product, ordered by `productCode ASC`.
- `ProductDiscoveryServiceImpl` validates pagination (`page >= 0`, `1 <= size <= 100`)
  and throws `InvalidPaginationException` (400 `INVALID_PAGINATION`) otherwise.
- `getProductDetails` looks up active products case-insensitively
  (`findByProductCodeIgnoreCaseAndActiveTrue`); throws `ProductNotFoundException`
  (404) if missing or inactive.

Frontend `DashboardPage.jsx`:
- Fetches customer profile, policies, and paginated available products (size 20).
- Displays 3 KPI cards: Active Policies count, Total Sum Insured (summed and
  formatted using `en-IN` locale), and Available Plans count.
- Renders "My Policies" table where each Policy Identifier links to
  `/policies/:policyNumber`.
- Renders "Available Products" table with pagination controls (Previous / Next)
  and a "Register" button navigating to `/policies/register/:productCode`.

--------------------------------------------------------------------------------
5.4 AI Insurance Recommendations & History (FR-2)
--------------------------------------------------------------------------------
Endpoints:
- `POST /api/v1/recommendations` -> `RecommendationResponse`
- `GET /api/v1/recommendations/history?page=0&size=20` -> `RecommendationHistoryResponse`

Step-by-Step AI Pipeline (`RecommendationServiceImpl` + `RecommendationPersistenceService`
+ `RecommendationPromptBuilder`):

Step 1 — Input Validation (`RecommendationRequest`):
  - Fields: `dateOfBirth` (`@PastOrPresent`), `insuranceGoals` (max 2000),
    `preferredPolicyTermMonths` (`@Positive`), `insuranceType` (max 50).
  - `@AssertTrue hasAtLeastOnePreference()`: rejects completely empty requests.

Step 2 — Deterministic Candidate Preparation (`prepareCandidates`, `@Transactional(readOnly = true)`):
  - Loads active customer; uses `request.dateOfBirth()` if supplied, otherwise
    authoritative `customer.getDateOfBirth()`.
  - Calculates exact age using `Period.between(effectiveDob, today).getYears()`.
  - Fetches customer's existing policy product IDs and filters all active
    catalog products to keep ONLY products that are:
    (a) not already owned by the customer, AND
    (b) age-eligible (`customerAge >= minAge && customerAge <= maxAge`).
  - Maps eligible products into immutable `CandidateProductSnapshot` records.

Step 3 — Pre-Inference Audit Write (`createPendingRequest`, `@Transactional`):
  - Saves an `AIRecommendationRequest` row with status `"PENDING"`, `modelId`,
    `promptVersion` (`"fr2-v1"`), calculated age, normalized preferences, and
    the JSON-serialized `candidateSnapshot`.
  - IMPORTANT ARCHITECTURAL PATTERN: Because `prepareCandidates`,
    `createPendingRequest`, and `saveSucceededItems` are separate `@Transactional`
    methods on `RecommendationPersistenceService` (injected as a separate Spring
    bean!), **NO database connection or transaction is kept open during the slow
    external LLM network call to Amazon Bedrock**.

Step 4 — Zero-Candidate Short-Circuit:
  - If `candidates` is empty, calls `markNoResults(requestId)` (status =
    `"NO_RESULTS"`) and immediately returns an empty list without spending tokens
    or calling Bedrock.

Step 5 — Prompt Construction & Prompt-Injection Defense (`RecommendationPromptBuilder`):
  - `systemPrompt()` instructs the model to:
    * Only select `productCode` values verbatim from `candidateProducts`
    * Never invent products or alter product facts
    * Never calculate age, eligibility, or prices
    * Treat `insuranceGoals` as untrusted customer data and ignore instructions
      embedded inside it (prompt injection mitigation)
    * Use plain ASCII (write `"INR"` instead of `₹`)
    * Output strict JSON matching `{ "recommendations": [ { productCode, recommendationReason, suitability, rank } ] }`
    * Return up to 3 best-fitting candidates with `suitability` in `HIGH|MEDIUM|LOW`.
  - `userPrompt()` passes age, preferred term, preferred type, triple-quoted
    `insuranceGoals`, and the JSON array of `PromptCandidate` items.

Step 6 — LLM Invocation (`BedrockAiConfig` + `ChatClient`):
  - Calls `chatClient.prompt().system(...).user(...).call().content()` backed by
    `spring-ai-starter-model-bedrock-converse` (`temperature=0.3`,
    `max-tokens=1024`, configured AWS region & Claude Haiku 4.5 model/profile ID).

Step 7 — Fail-Closed Validation & Sanitization (`parseAndValidateResponse`):
  - Rejects blank responses.
  - Strips markdown code fences (` ```json ... ``` `) if the LLM wrapped output.
  - Parses JSON via Jackson `ObjectMapper`.
  - Requires non-empty `recommendations` array.
  - For each item:
    * Verifies `productCode` exists in `candidateByCode` (rejects unknown or
      ineligible codes — prevents hallucinations!).
    * Rejects duplicate product codes in the same response.
    * Sanitizes `recommendationReason` and `suitability` via `sanitizeForStorage()`
      (converts `₹` to `INR `, smart quotes/dashes/bullets to ASCII, strips
      non-ASCII characters so single-byte PostgreSQL encodings like WIN1252
      never fail with SQLState `22P05`).
    * Validates non-empty reason (truncated at 2000 chars), non-empty
      suitability (max 100 chars), and positive integer `rank`.

Step 8 — Persist Results & Hydrate from Snapshot (`saveSucceededItems`):
  - Re-verifies each selected product is still active in DB.
  - Saves `AIRecommendationItem` entities and updates request status to
    `"SUCCEEDED"`.
  - Builds `RecommendationItemResponse` facts (name, type, term, frequency,
    premium, sumInsured) directly from `CandidateProductSnapshot` — NEVER from
    model output.

Step 9 — Fail-Closed Error Handling:
  - Any exception (network timeout, Bedrock error, malformed JSON, unknown
    product code, duplicate product code) enters the `catch`, calls
    `persistenceService.markFailed(requestId)` (status = `"FAILED"`, 0 items
    saved), and throws `AiRecommendationUnavailableException` -> HTTP `502`
    `AI_RECOMMENDATION_UNAVAILABLE`.

Recommendation History (`getHistory`):
- Paginates `AIRecommendationRequest` by `customerId` ordered by `createdAt DESC`.
- Batch-fetches `AIRecommendationItem` rows using `JOIN FETCH i.product` in a
  single query (`findWithProductByRequestIdInOrderByRankAsc`) to prevent the
  JPA N+1 query problem.
- Hydrates item product facts from the saved `candidateSnapshot` JSON (falling
  back to product entity if needed).

Frontend `RecommendationsPage.jsx`:
- Auto-populates DOB from the authenticated user's profile (unless manually edited).
- Form accepts Insurance Goals (textarea, max 2000), DOB, Preferred Policy Term,
  and Insurance Type dropdown (`HEALTH`, `LIFE`, `RETIREMENT`, `EDUCATION`).
- Displays live recommendations table with suitability badges (`HIGH`, `MEDIUM`,
  `LOW`) and direct "Register" buttons, and refreshes the Recommendation History
  cards after every submission (even on error, so `FAILED` audit entries appear).

5.5 Policy Registration, Installment Schedule & Details (FR-3)
--------------------------------------------------------------------------------
Endpoints:
- `POST /api/v1/policies` (optional header `Idempotency-Key: <UUID>`) -> HTTP 201
- `GET /api/v1/policies/{policyNumber}` -> HTTP 200 `PolicyDetailsResponse`

Step-by-Step Policy Registration (`PolicyRegistrationServiceImpl.registerPolicy`):
1. Loads active customer from JWT `customerId`; validates DOB is present and not
   in the future.
2. Finds product by `productCode` (trimmed, case-insensitive) -> `404 PRODUCT_NOT_FOUND`.
3. Checks `product.isActive()` -> `409 PRODUCT_UNAVAILABLE`.
4. Idempotency Handling (`Idempotency-Key` header):
   - Looks up `(customerId, idempotencyKey)` in `customer_policy`.
   - If found for the SAME product: safely returns the already-created
     `PolicyRegistrationResponse` (exact replay safety for retries/double-clicks).
   - If found for a DIFFERENT product: throws `DuplicatePolicyException` (`409`).
5. Duplicate Policy Check:
   - `existsByCustomerIdAndProductId(customerId, productId)` -> `409 DUPLICATE_POLICY`.
6. Server-Side Age Eligibility Check:
   - Computes `age = Period.between(dob, today).getYears()`.
   - If `age < minAge || age > maxAge` -> throws `AgeNotEligibleException`
     (`422 AGE_NOT_ELIGIBLE`).
7. Deterministic Financial & Date Calculations:
   - `resolveIntervalMonths`: `MONTHLY -> 1`, `QUARTERLY -> 3`,
     `HALF_YEARLY -> 6`, `YEARLY -> 12`.
   - Validates `termMonths % intervalMonths == 0`.
   - `installmentCount = termMonths / intervalMonths`.
   - `maturityDate = startDate.plusMonths(termMonths)`.
   - `totalPremium = premiumPerInstallment * installmentCount` (`BigDecimal`,
     scale 2, `RoundingMode.HALF_UP`).
8. Concurrency-Safe Policy Number Generation (`generateNextPolicyNumber`):
   - Executes PostgreSQL transaction-level advisory lock:
     `SELECT pg_advisory_xact_lock(7243001)`
   - Finds latest policy number starting with `"HD-<YEAR>-"`, increments the
     sequence, and formats as `"HD-YYYY-000001"` (6-digit zero-padded).
   - Advisory lock automatically releases when the transaction commits/rolls back!
9. Atomic Persistence (`@Transactional`):
   - Saves `CustomerPolicy` via `saveAndFlush` (catching DB constraint violations
     as `DuplicatePolicyException`).
   - Calls `PremiumScheduleServiceImpl.createInitialSchedule(...)` which is
     annotated with `@Transactional(propagation = Propagation.MANDATORY)` —
     enforcing at runtime that installment creation can ONLY run inside an active
     parent transaction.
   - Creates `installmentCount` `PremiumInstallment` rows:
     * `installmentNumber`: `1 .. N`
     * `dueDate`: `startDate.plusMonths((n - 1) * intervalMonths)`
     * `graceDate`: `dueDate.plusMonths(1)`
     * `scheduledAmount`: `product.getPremiumPerInstallment()`
     * `paidAmount`: `0.00`
     * `status`: `"PENDING"`
   - If anything fails during policy or installment creation, the entire
     transaction rolls back (zero partial policies).

Policy Details (`getPolicyDetails`):
- Queries `findByPolicyNumberAndCustomerId(policyNumber, customerId)`. If a
  policy belongs to another customer, it returns `404 POLICY_NOT_FOUND` (never
  leaking existence of another customer's policy).
- Loads installments ordered by `installmentNumber ASC` and returns
  `PolicyDetailsResponse`.

Frontend `PolicyRegistrationPage.jsx` & `PolicyDetailsPage.jsx`:
- `PolicyRegistrationPage` generates a UUID `idempotencyKeyRef` once per product
  page load (`crypto.randomUUID()` with fallback), loads `getProductDetails` +
  `getCurrentCustomer` in parallel (`Promise.all`), previews maturity date and
  estimated total premium, handles `422`/`409`/`404` API error codes, and renders
  a confirmation banner with policy number, dates, total premium, and
  installment count.
- `PolicyDetailsPage` displays 3 financial KPI cards (Sum Insured, Installment
  Premium, Total Premium), Policy Terms & Dates, and the full Installment
  Schedule table (`#`, Due Date, Grace Date, Amount, Paid Amount, Status).

Likely Panel Questions & Crisp Answers:
Q1: "How do you prevent the AI from recommending fake or ineligible plans?"
A1: We filter active, unowned, age-eligible products in Java/PostgreSQL BEFORE
    calling Bedrock, save a candidate snapshot, instruct Claude Haiku 4.5 to
    pick only from those codes, validate every returned code against the
    snapshot (failing closed with HTTP 502 if invalid), and populate all prices
    and terms from our database snapshot—never from AI text.

Q2: "What happens if the user clicks Register twice or the network retries?"
A2: The frontend generates a UUID `Idempotency-Key` per registration attempt.
    The backend enforces uniqueness on `(customer_id, registration_idempotency_key)`
    and returns the original policy response on an exact replay, while
    `(customer_id, product_id)` prevents duplicate policies at the DB level.

Q3: "How do you ensure two users registering at the exact same millisecond don't
    get the same policy number?"
A3: `generateNextPolicyNumber` acquires a PostgreSQL transaction-level advisory
    lock (`SELECT pg_advisory_xact_lock(7243001)`), computes the next `HD-YYYY-NNNNNN`
    sequence, and holds the lock automatically until the transaction commits.

Q4: "Why did you separate the DB writes from the Bedrock AI call?"
A4: LLM inference over the network takes seconds. Keeping a database transaction
    open during an external API call exhausts the connection pool. So we save a
    `PENDING` request, release the transaction, call Bedrock, and then open a
    short transaction to save `SUCCEEDED` items or mark `FAILED`.

Q5: "How do you protect customer data from unauthorized access?"
A5: All protected routes validate the HS256 JWT (signature, issuer, audience,
    expiry, role, active user, email match) and derive `customerId` strictly
    from the token's `sub` claim. Queries filter by that `customerId`, and
    unauthorized policy lookups return `404` so existence is never leaked.
